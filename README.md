# 트러블슈팅 및 성능 개선
## 1. 스레드 점유와 Webflux 도입

### 문제

AWS EC2 t3.micro 환경에서 30 클라이언트에서 자동매매를 동시 요청했을 때 CPU Utilization이 90%를 초과

### 문제 진단

Spring MVC 단일 서버 구조에서

WebSocket 으로 실시간 주가를 수신하고, 반복문으로 조건을 검증하는 로직.

Spring Tomcat 모델은 스레드 블로킹 모델이기 때문에 위의  상황에서 사용자가 취소하기 전까지 스레드를 점유하여 CPU를 갉아먹음.

### 대안
1. Thread.sleep() 과 Jitter 도입

    - 장점
      - 명시적으로 스레드를 쉬게하고, 랜덤한 시간에 깨워 CPU 친화적으로 만듬
    - 단점 
      - 실시간성 저하
      - OS recv buffer 가 가득차 데이터 누락 가능성

2. Webflux 도입
   - 장점
     - 스레드 모델이 이벤트 루프 방식이기 때문에 작업이 I/O 비중이 크다면 더 많은 요청 감당 가능
     - 1번 대안의 단점을 커버
   - 단점
     - 러닝커브

### 결과
Webflux 도입.

CPU Utilization 90% 도달 기준으로 최대 동시연결 수가 30에서 400까지 증가 (약 1200% 개선)

## 2. GC로 인한 CPU 과부하와 I/O 병목 개선

### 문제
자동매매를 위해 1인당 하나의 WebSocket 세션을 열고 있음

400명 동시 처리 상황에서 요청 수를 늘리지 않음에도 시간이 지나면 CPU Utilization이 99%까지 증가하여 서버가 멈추는 상황 발생

### 문제 진단

증권사에서 실시간 시세를 보내는 패킷의 크기는 4KB~6KB 이고, 그 것을 초당 인당 10개씩 400명이 받음.

그 것을 직렬화하고, 필요한 데이터만 추출하여 DTO로 생성하여 Young GC가 1~2초에 한번씩 발생.
너무 많은 직렬화로 인해 GC가 발생하여 처리가 밀리는 것으로 판단 

### 대안
1. 바이너리를 직접 파싱
    - 장점
      - 직렬화와 DTO를 추가 생성하지 않으므로 불필요한 객체 생성을 줄일 수 있음
    - 단점
      - 확장성이 제한됨
      - 다루기가 너무 힘듬

2. 서버 내 종목 데이터가 있으면 공유하기
   - 장점
     - Websocket 세션의 수와 직렬화를 줄일 수 있음
   -  단점
     - 세션 관리가 필요함

### 결과
서버 내 수신중인 종목을 자료구조로 관리.
한국 장 총 주식 종목 수 3000개 중 2000 종목은 사람들이 조회를 하지 않음.

즉, 1개의 종목 데이터를 3명이서 공유한다고 가정했을 때 66% 의 성능 개선을 기대할 수 있음.

400 동시연결에서 CPU Utilization 이 60% 대에서 안정화되었으며, GC로 인해 요청이 밀리지 않음.




## 3. Redis Pub/Sub Stampede

### 문제
AWS ASG 를 도입하여 8개의 서버 인스턴스가 동시에 떠 있는 상황.
특정 종목의 정보를 제공하는 사용자의 세션 종료시 , 해당 종목을 수신받던 사용자 들이 일제히 증권사 API 호출을 하는 Cache Stampede와 같은 현상 발생

### 문제 진단
세션 복구 과정에서 동일 종목에 대한 동시성 제어 부재

### 결과
Redis Lua 스크립트 기반 분산 락 적용으로 최초 1회만 실제 재구독 수행


## 4. 주문의 중복 처리 방지와 멱등성 부여


### 문제

## 문제 진단 

주가가 유저가 설정한 기준가에 멈춰서 오르내리고는 것을 반복함

특정 시간과 이벤트에 대해 멱등성의 부재

## 결과

중복 감지, 재시도, 장애 복구 상황에서도 중복 주문 방지

## 5. 애플리케이션 DB 커넥션 풀 병목 해소

### 문제

주식 관리를 위한 정보를 저장하는 기능에 대해 10,000 동시 INSERT 테스트 상황에서
커넥션 대기 수 (R2DBC pending acquire) 와 에러율 급증

### 문제 진단
Mysql의 max_connections은 꽉 채운 상태이나 CPU 사용률이 40% 대를 유지함.
이는 DB의 처리능력은 여유가 있으나 그에 비해 애플리케이션 커넥션 풀이 부족한것으로 보임.

실제로 INSERT 테스트 대상 테이블의 의존관계가 복잡하지 않고, 쿼리도 단순함

### 대안
1. 커넥션풀 조정
   - 장점
     - 간단하게 해결 가능
   - 단점
     AWS 공식문서에서 RDS의 커넥션 설정은 웬만하면 건드리지 말라고 명시되어있음.


2. 서버 인스턴스 늘리기
   - 장점
     - 간단함
   - 단점
     - 비쌈
     
3. Batch Bulk Insert
   애플리케이션에 버퍼를 두고, INSERT 요청이 들어오면 이벤트 메세지 발송.

   10개를 모아서 Bulk Insert 시도한 후 성공하면 Kafka offset commit.

    - 장점
      - 애플리케이션 레벨에서 요청 처리량 개선 가능
    - 단점
      - 이벤트 발행이 필요하고, 그에 따라 멱등 처리와 동시성 등 관리 포인트가 늘어남
      
### 결과

Batch Bulk Insert 채택.

동시 10000 Insert 테스트에서 에러율 0% 기록하였고 p99 20ms 수준.




결과: p95 450ms → 150ms로 개선
